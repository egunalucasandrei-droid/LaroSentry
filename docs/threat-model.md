# Threat model

Public test pilot (2026-10-17): the Render origin is internet-accessible with synthetic fixtures and real session/role/MFA/CSRF checks. Public traffic can exhaust free quotas; single-process memory throttles are not persistent or distributed abuse protection. Sleep pauses maintenance; database expiration has no managed backup. Use synthetic information, protect fixture passwords/MFA and monitor quotas. External database access is disabled; migration credentials are absent from the web service. New accounts cannot bypass unavailable contact verification. A commercial launch or Hostinger move requires separate provider/restore/operations/security review. [Current boundaries](render-pilot.md).

Onboarding extension (2026-10-16) covers restricted-session privilege bypass, duplicate-contact enumeration, SMS cost abuse/code guessing/replay, stale contact verification, host intent being mistaken for a grant, cross-applicant ID access, malicious uploads and invitation privilege escalation. Controls include account/role/permission gates, generic registration outcomes, channel/challenge binding, persistent sending/attempt limits, contact/session invalidation, manual facility-specific approval, strict raster decoding/re-encoding with pixel/byte budgets, encrypted private storage and assigned-reviewer document checks. Local SMS is intentionally simulated; real provider delivery, backup expiry and production key/operational/legal review remain external setup. [Details](onboarding-verification.md).

Role workspace extension (2026-10-16) covers direct owner/staff URLs, forged grants, cross-facility queries, booking-only staff reading payments, self-payment verification, stale staff sessions and publishing unapproved facilities. Controls are server-side membership/permission scopes, unchanged MFA/CSRF, exact-account staff grants excluding OWNER/ADMIN, target session revocation, minimized projections, self-verification denial and approval-gated publication with reasoned decisions. Workspace switching grants no authority. Report narratives/reporter identities remain private to the reporter/admin. [Current role matrix and limits](role-workspaces.md).

NOLTA extension (2026-10-16): new threats include editing another host's court, racing a settings update against confirmation, stale price acceptance, cross-facility rescheduling, replaying a previously privileged manual reservation, and resetting unrelated bookings. Controls are OWNER-scoped API queries and mutations, MFA/local-demo boundaries, parameterized queries and bounded schemas, court locks and allocation exclusion, reviewed price/policy plus idempotency checks, same-facility reschedule validation, and a narrowly guarded archive reset with preview fingerprint/audit trail. Human operators remain responsible for honoring existing reservations when deactivating or changing normal hours. The reset intentionally does not physically delete immutable historical evidence.

Local demonstration boundary: password-confirmed demo access intentionally omits the second factor for three exact privileged fictional accounts. A person holding those demo passwords can exercise their authorized demo permissions. Containment requires the explicit launcher flag, matching timestamped demo database on loopback, short-lived in-memory session authorization and unchanged role/resource checks. Never place real user data in the demo database. Production and ordinary accounts cannot use this path. The UI identifies this as demonstration access, not MFA verification. This convenience does not establish production readiness.

Assets: session/CSRF secrets, account credentials and MFA, private reservations, facility permissions, allocation integrity, financial records, verification/reset links, audit history and backup keys.

External map tiles are a third-party privacy boundary and are loaded only in map view. Do not test the provider's infrastructure. Outage of maps must leave list discovery usable. SMTP failure leaves committed booking records intact and retries through the outbox.

Community threats include forwarded private links, accidental publication, leaked rosters and over-capacity acceptance. Recipient authorization, explicit publication, blocked mode changes with active players, minimal summaries and booking row locks address these paths. Invitation attempts use generic responses; this is not a claim of timing-indistinguishable account existence. Organizer roster access is intentionally limited to accounts with which they have a participation/invitation relationship. Expanded anti-spam controls and moderation remain work.

## Admin-specific threats and boundaries

- Direct API/URL privilege escalation: namespace-wide ADMIN/MFA enforcement, per-controller and per-record checks, explicit frontend denial for all non-admin roles. Registration and school-email domains cannot grant admin access.
- Stale or concurrent administrative access: a shared database transaction lock and fresh session/role lookup protect mutations; revocation/restoration invalidates sessions. Self-restriction is denied and local revocation preserves another MFA-ready admin. Concurrent cross-restriction is tested.
- Unreviewed facility publication: applications create PENDING facilities; only an independent admin approval publishes and grants scoped ownership. Clarification/rejection reasons are attributable and immutable.
- Excessive inspection and leakage: explicit user projections, paginated lists, bounded histories, read audit for user/report/application details, no exports/files, minimal error logging. Authorized admins still see submitted reports and account identifiers for review; operator misuse remains a human/process risk.
- Unfair punishment or conflict of interest: no automatic restrictions from alerts, reason and explicit confirmation for decisions, own-report/application decision denial, reversible restrictions and review history.
- Alert false positives and missed activity: supporting event IDs and published rules support human interpretation. Shared IPs, forgotten MFA and test activity can trigger alerts. The bounded scan has no guarantee of complete detection after long outages/overload; health exposes last scan and truncation.
- Malicious report/clarification text: server length/type validation, parameterized queries and React text rendering. Do not copy submitted markup into trusted HTML. No attachments are accepted.

The local operator holding database credentials remains trusted and can grant ADMIN using the documented exact-account command. Protect the workspace and OS account. Database owners can still alter append-only data. Backups, production monitoring, incident response and independent security assessment remain separate operational work.
